# Swagger / OpenAPI Guide

This project must use `@nestjs/swagger` with its CLI plugin for API route contracts when Swagger/OpenAPI documentation is added or expanded.

Goal: generate schemas from TypeScript DTO classes, class-validator decorators, controller signatures, and JSDoc comments. Do not maintain Swagger schemas manually.

Current project note: the API does not currently have `@nestjs/swagger` wired in. Treat this file as the rulebook for the first Swagger slice.

AI agent rule: before changing controllers, request DTOs, response DTOs, route return types, or Swagger setup, read this file unless these rules are already present in the active context.

## Main Rule

When the plugin is configured correctly, do not write manual `@ApiProperty`, `@ApiResponse`, `@ApiBody`, or other `@Api*` decorators by default.

If a schema is empty, missing a field, or showing the wrong type, fix the DTO/controller/plugin rule that caused it. Do not paper over the problem with manual decorators unless Yan explicitly approves an exception.

Every route should expose autogenerated request and response schemas:

- request bodies come from request DTO classes and class-validator decorators
- response bodies come from explicit controller return DTO classes
- params/query objects should use DTO classes when they are non-trivial
- JSDoc comments on DTO fields provide field descriptions

## How The Plugin Works

The plugin is a TypeScript transformer that runs at compile time.

It reads:

- DTO classes
- controller method signatures
- class-validator decorators
- JSDoc comments when `introspectComments: true`

Then it injects Swagger metadata into the emitted JavaScript before runtime.

Consequence: anything erased by TypeScript is invisible to Swagger. Interfaces, type aliases, string literal unions, and `import type` can break schemas in DTO/controller files.

## DTO Rules

### 0. DTO Folder Layout

DTO files must not live flat under `dto/`.

Use this layout inside each HTTP adapter/module:

```text
dto/
  request/
    create-order.dto.ts
  response/
    order-response.dto.ts
  shared/
    weekly-schedule.dto.ts
```

Rules:

- Request body, query, and param DTOs go in `dto/request`.
- Response DTOs go in `dto/response`.
- `dto/shared` is allowed only for small nested contract classes reused by both request and response DTOs.
- Do not import request DTOs from response DTOs or response DTOs from request DTOs.
- Controllers may import from `dto/request` and `dto/response`.
- Mappers should import response DTOs from `dto/response`.
- Avoid barrel exports for DTO folders until Swagger generation is wired and stable.

### 1. DTOs Are Classes

Use classes for request and response DTOs.

```ts
export class OrderResponseDto {
  public readonly id!: string;
}
```

Do not use interfaces or type aliases for DTOs used by controllers.

```ts
export interface OrderResponseDto {
  id: string;
}

export type OrderResponseDto = {
  id: string;
};
```

### 2. Enums Are Real Runtime Enums

Use `enum`, not string literal unions, for values that must appear as OpenAPI enums.

```ts
export enum PaymentMethodDto {
  Pix = 'pix',
  CreditCard = 'credit_card',
  DebitCard = 'debit_card',
}
```

Avoid:

```ts
export type PaymentMethodDto = 'pix' | 'credit_card' | 'debit_card';
```

### 3. No `import type` In DTO Or Controller Files

Use regular imports for anything referenced by DTOs or controller method signatures.

```ts
import { OrderResponseDto } from './order-response.dto';
import { PaymentMethodDto } from './payment-method.dto';
```

Avoid:

```ts
import type { OrderResponseDto } from './order-response.dto';
import type { PaymentMethodDto } from './payment-method.dto';
```

`import type` is fine in pure domain/application code that does not feed Swagger metadata.

### 4. Validate Enums With `@IsEnum`

```ts
@IsEnum(PaymentMethodDto)
public readonly paymentMethod!: PaymentMethodDto;
```

Avoid `@IsIn([...])` for Swagger-visible enum fields.

### 5. Use Concrete Types

Preferred:

- `string`
- `number`
- `boolean`
- `Date`
- DTO class references
- DTO arrays like `OrderItemDto[]`
- nullable values like `string | null`

Avoid in DTOs:

- `any`
- `unknown`
- `object`
- `Record<string, any>`
- anonymous inline object types
- unions like `FooDto | BarDto` without a deliberate discriminator design

### 6. class-validator Drives Schema

Every request DTO field should have class-validator decorators that express type and constraints.

Common decorators:

- `@IsOptional()`
- `@IsString()`
- `@IsInt()`
- `@IsNumber()`
- `@IsBoolean()`
- `@IsUUID()`
- `@IsEmail()`
- `@IsDate()`
- `@IsEnum(EnumName)`
- `@Min(n)` / `@Max(n)`
- `@MinLength(n)` / `@MaxLength(n)`
- `@IsArray()`
- `@ArrayMinSize(n)`
- `@ValidateNested({ each: true })` with `@Type(() => ChildDto)`

### 7. Use JSDoc For Descriptions

With `introspectComments: true`, JSDoc comments become schema descriptions.

```ts
export class CreateOrderRequestDto {
  /** Scheduled pickup or delivery time in ISO format. Null means immediate order. */
  @IsOptional()
  @IsDateString()
  public readonly scheduledFor?: string;
}
```

Do not add `@ApiProperty({ description: '...' })` for normal descriptions.

### 8. Field Style

Request DTOs should use top-level fields because `ValidationPipe` and class-transformer hydrate them from JSON:

```ts
export class CreateOrderRequestDto {
  @IsString()
  public readonly customerName!: string;
}
```

Response DTOs can use constructor parameter properties when they are built manually by mappers:

```ts
export class OrderResponseDto {
  public constructor(
    public readonly id: string,
    public readonly total: number,
  ) {}
}
```

If response DTOs use constructor parameter properties, the Swagger plugin must be configured with `parameterProperties: true`.

## Required Nest CLI Config

When Swagger is introduced, update `apps/api/nest-cli.json`:

```json
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "plugins": [
      {
        "name": "@nestjs/swagger",
        "options": {
          "dtoFileNameSuffix": [".dto.ts", "Dto.ts"],
          "controllerFileNameSuffix": [".controller.ts", "Controller.ts"],
          "classValidatorShim": true,
          "introspectComments": true,
          "parameterProperties": true
        }
      }
    ]
  }
}
```

## Required Bootstrap

When Swagger is introduced, wire it in `apps/api/src/main.ts` after global pipes and before `listen`.

```ts
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';

const config = new DocumentBuilder()
  .setTitle('Bem Comer API')
  .setVersion('1.0')
  .build();

SwaggerModule.setup('docs', app, SwaggerModule.createDocument(app, config));
```

With the existing global prefix, expected routes are:

- Swagger UI: `/docs`
- JSON: `/docs-json`
- YAML: `/docs-yaml`

Confirm the actual routes after implementation because global-prefix behavior can vary by setup.

## Rebuild After Changes

The plugin runs at TypeScript compile time.

After changing DTO classes, enums, controller signatures, or `apps/api/nest-cli.json`, restart/rebuild:

```bash
pnpm --filter api build
pnpm --filter api dev
```

If schemas look stale, restart the dev server and delete `apps/api/dist` if needed.

## Troubleshooting

| Symptom | Likely Cause | Fix |
| --- | --- | --- |
| Field appears as `{}` | Type alias, interface, string union, or `import type` | Use runtime class/enum/regular import |
| Response schema is empty | Interface return type or constructor props without `parameterProperties` | Use class return type and plugin option |
| DTO missing entirely | Filename does not match configured suffix | Rename file or update suffix config |
| Field missing | Missing class-validator/type metadata | Add explicit decorators/type |
| Enum shown as plain string | Used string union or `@IsIn` | Use real enum and `@IsEnum` |
| Nested object is generic `object` | Missing nested decorators | Add `@ValidateNested` and `@Type` |
| Changes do not show | Plugin did not rerun | Rebuild/restart dev server |

## Quick Checklist For New DTOs

- [ ] DTO is a `class`, not `interface` or `type`.
- [ ] Swagger-visible enums are real `enum`.
- [ ] No `import type` in DTO/controller files for Swagger-visible references.
- [ ] Request DTO fields have class-validator decorators.
- [ ] Optional fields use `@IsOptional()`.
- [ ] Enum fields use `@IsEnum(EnumName)`.
- [ ] Nested DTOs use `@ValidateNested({ each: true })` and `@Type(() => ChildDto)` when needed.
- [ ] JSDoc comments describe public API fields.
- [ ] Controller methods have explicit `Promise<ResponseDto>` return types.
- [ ] Response DTO constructor parameter properties are used only with `parameterProperties: true`.
- [ ] No manual `@Api*` decorators unless explicitly approved.

## Boundary Rule

Swagger DTOs are adapter-layer contracts. They must not become domain objects.

Map between:

- HTTP request DTOs
- application commands
- domain objects/value objects
- response DTOs/read models

Do not let Swagger, class-validator, or class-transformer decorators leak into `domain` or core `application` code.
